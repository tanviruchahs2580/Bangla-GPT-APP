Why minor and not major: the changes since `v0.9.2` are delivered features,
security hardening and documentation — the CHANGELOG's "Unreleased" section is
the record (`CHANGELOG.md`, generated). No documented route, request shape or
environment variable was removed. If the owner's plan is to make this the
public launch, `v1.0.0` is equally defensible; that is a product decision, and
the plan below only fixes the mechanics. **The version bump is a repository
edit that must happen before tagging** — `check_version.py` (CI) fails
otherwise, which is the point of the single-source rule.

## Release notes skeleton

The workflow does not need a hand-written body: it calls GitHub's
`generate-notes` API for the compare range and appends the two image digests
(`.github/workflows/release.yml`). If the owner prefers hand-written notes,
this is the shape to fill in — Keep a Changelog order, and no claim that is not
in the CHANGELOG:

```markdown
## v0.10.0 — <date>

<one paragraph: what this release is for, in the reader's terms>

### Added
- <user-visible addition, tracing to a CHANGELOG line>

### Changed
- <behaviour change and who notices>

### Fixed
- <defect, with the finding id when it came from the audit>

### Security
- <hardening item>

### Upgrade notes
- Migrations: `alembic upgrade head` runs N revisions from v0.9.2
  (head c6e8a0b2d4f6). Back up first (`docs/backup_dr.md`).
- Environment: <new/changed variables, or "none">
- Images: `ghcr.io/tanviruchahs2580/bangla-gpt-api:v0.10.0` and
  `…/bangla-gpt-web:v0.10.0`; no `:latest` by design.

### Not in this release
- <deferred items with issue links, so silence is not read as "done">
```

## Rollback plan

| Layer | Action | Where it is documented |
| --- | --- | --- |
| Release | Redeploy the previous tag: `git checkout v0.9.2`, `export API_TAG=v0.9.2 WEB_TAG=v0.9.2`, `docker compose --profile core pull && up -d --wait` | [../runbook.md](../runbook.md) §7 (the release workflow performs this automatically on a failed `compose up` or failed post-deploy health gate) |
| Database | `alembic downgrade <v0.9.2 revision>` after a backup; tables introduced after v0.9.2 lose their data (the downgrade drops them) | [../runbook.md](../runbook.md) §7, §4 |
| Partial | Disable the feature via its environment variable or flag rather than rolling the whole release back — decide per change during triage | [../runbook.md](../runbook.md) §7–§8 |
| Verification after rollback | `/health`, `/ready` 200, login, one tutor turn, one quiz submit, error rate back to baseline | [../runbook.md](../runbook.md) §7 |

The rollback target is deliberately the previous *tag*, not "the last commit":
tags are what the images are named after, so a non-tag rollback has no image to
pull.

## Owner actions (not executed by the audit)

Run in this order, after the preconditions are green, from a clean clone of
`main` at the merge commit:

```bash
# 1. bump every version field, regenerate the changelog, open the PR
git switch -c chore/release-v0.10.0
python scripts/check_version.py            # after editing pyproject.toml + web package.json + README + deployment guide
python apps/api/scripts/gen_changelog.py
git commit -am "chore(release): v0.10.0"
# 2. after that PR merges and its CI is green on main:
git tag -a v0.10.0 -m "Bangla GPT v0.10.0"
git push origin v0.10.0
# 3. watch the release workflow (it creates the GitHub Release and deploys only
#    when vars.DEPLOY_ENABLED == 'true')
gh run watch "$(gh run list --workflow release.yml --limit 1 --json databaseId -q '.[0].databaseId')"
```

repository: publish the 13 existing tags as GitHub Releases or explicitly
