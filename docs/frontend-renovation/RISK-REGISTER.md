## B. Findings NOT changed — preserved pending an owner decision

These are deliberately **not** silently "fixed". Either the fix would change an interaction
contract the feature lock names explicitly (master-prompt §0.3 invariant 9), or it needs a
design/product decision this task is not authorised to make.

| ID | Sev | Finding | Why it is not changed | Recommendation |
|---|---|---|---|---|
| R-13 | **P2** | Four destructive actions take effect with **no confirmation**: delete a saved note, delete an offline chapter copy, revoke a guardian invite code, revoke a school invite. | §0.3 lists "confirmations" and "submission behavior" as locked. Adding a confirm changes the number of steps an existing workflow takes — an observable interaction-contract change, not a presentation change. It is also demonstrably *intended* in places: `savedNotes.test.tsx` asserts the current single-step delete behaviour. | Product owner decides whether delete-note / revoke-invite gain a confirm step. The offline-copy case is the strongest candidate (an accidental tap frees nothing back and loses a downloaded chapter). |
| R-14 | **P2** | `pages/SchoolDashboard.tsx:9` documents itself as serving "school_admin / admin", but the route gate in `App.tsx:395-401` is `role="school_admin"` only, so a platform `admin` is redirected to `/admin`. | Whether a platform admin *should* see `/school` is a permissions/product question. Widening a frontend role gate is exactly the "frontend-only authorization" trap the prompt forbids, and the server remains the authority. | Confirm the intended role matrix for `/school`, then align route + doc comment + server policy together in one change. |
| R-15 | **P2** | The progress-ring **arc-vs-track** boundary is below 3:1: **1.55:1 light / 2.81:1 dark**. The arc is read by hue, not luminance. Fixing it needs a three-level gauge (surface → track → arc) where each level clears 3:1 against its neighbour. | A three-level gauge is a visual-design change to a component with reviewed baselines, not a defect with one unambiguous correction. The *track* fix (R-05) was unambiguous and is done. | Design decision: either accept hue-differentiation (and record the WCAG 1.4.11 judgement), or author a three-level gauge and re-baseline. |
| R-16 | **P3** | `.card`'s mixed border `color-mix(--line 75%)` renders at **1.22:1 light / 1.17:1 dark** against `--card` — weaker than the base `1px var(--line)` it replaced, and below 3:1. | The card border is decorative, not a control edge (the *control* boundary is `--line-strong`, which is asserted). Raising it changes the look of every card in the product. | Low priority. If card edges should be perceptible, move them to `--line-strong` and re-baseline. |
| R-17 | **P3** | `MePage.tsx:504` renders the server string `on_disable_note_code` through `t()` with a raw-value fallback, so an unmapped code can surface as machine text to a child. | The correct copy for each code is a content decision, and the key set is owned by the API. Guessing translations for codes whose meaning is not documented here would be worse than the fallback. | Enumerate the `on_disable_note_code` values from the API and add a localized key each. |
| R-18 | **P3** | `SCH-SEC-001` calls `getSchoolStudents(100, 0)` — page 1 only, with no UI affordance indicating truncation. | The API already supports pagination; adding school pagination is a **new capability**, which §0.3 invariant 6 forbids under a renovation. | Product backlog: add pagination to the school students section. |
| R-19 | **P3** | The Makefile `seed` target is broken: from `apps/api` it resolves `../apps/web/e2e/seed_e2e_users.py`, i.e. `apps/apps/web/...`, which does not exist. | Build tooling, outside this frontend scope, and possibly owned by another stream. Worked around rather than edited. | One-line fix: `../web/e2e/seed_e2e_users.py`. |

## C. Renovation risks carried and how they are controlled

| ID | Risk | Control |
|---|---|---|
| R-20 | A CSS change breaks a surface nobody looked at. | The 60 Playwright visual baselines across 5 screens × light/dark × bn/en × 3 viewports are the net. Any failure is reviewed before re-baselining; `--update-snapshots` is never run blind. |
| R-21 | The app-entry bundle exceeds its 125,000 B gzip budget. Baseline was 112,989 B (90.4 %). | No dependency was added and no new entry-chunk code was introduced by this renovation; the budget plugin re-runs on every build and its output is captured in the final evidence. |
| R-22 | A guard is written that cannot fail. | Each new guard was **negatively tested**: the hero-placeholder assertion was demonstrated to fail with the old `#6b7a66` (4.242 < 4.5), and the SchoolsCard test to fail with the old `.catch`. A guard that has never been seen to fail is not evidence. |
| R-23 | Renovation accidentally changes a behaviour contract. | `FEATURE-LOCK-REGISTER.md` lists 25 routes and ~200 capability rows with `file:line`; §10 of that file lists 12 cross-cutting untouchable contracts. Every code change in this delivery is presentation, feedback, copy or element-semantics — no handler, API call, permission, validation rule or state transition was altered. |
| R-24 | Baseline defect mistaken for a regression. | The baseline gate set was captured **before** any edit and is reproduced in `BASELINE-AND-REPOSITORY-AUDIT.md` §3. The CSS minify warning in §3.2 is explicitly labelled a baseline defect. |
