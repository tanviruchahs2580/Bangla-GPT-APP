# S6.8 — Game-day drill: 10x load + LLM-down degraded mode

Date: 2026-09-08 · Environment: local Windows dev host, throwaway
instances on :8010 (mock LLM, temp copy of dev DB, rate limits lifted
for the capacity run only) and :8020 (Gemini provider pointed at an
invalid key). The preview stack (:8000/:4174) and the real Gemini quota
were NOT used for any of this — drill DBs were `mktemp` copies, deleted
afterwards.

## Leg 1 — Rate-limiter drill (accidental, valuable)

First ladder run used production limits (30 tutor-asks/min/user).
One synthetic student hammering 210 asks/level produced a flat ~70 %
error share = exactly the ask portion of traffic, all HTTP **429**
(health checks 100 % green). Verdict: **per-user backpressure works
under burst**; abusive demand is shed cleanly instead of queuing.
This also flagged the probe metric itself (429 counted as "error") —
correct for a capacity run, so leg 2 lifted the limit.

## Leg 2 — Capacity ladder (1 uvicorn worker, mock LLM, dev SQLite)

`scripts/concurrency_probe.py` — 70 % tutor asks / 30 % reads,
300 req/level, limits lifted:

| Concurrency | Errors | p50 ms | p95 ms | RPS |
|---:|---:|---:|---:|---:|
| 1 | 0 % | 14 | 19 | 77 |
| 10 | 0 % | 159 | 204 | 69 |
| 30 | 0 % | 450 | 624 | 70 |
| 60 | 0 % | 997 | 1 248 | 61 |
| 120 (G6 pilot peak) | 0 % | 1 616 | 1 907 | 66 |
| 240 (2x headroom) | 0 % | 2 569 | 3 454 | 60 |

Readings:

- **Zero failed requests at 240-way concurrency** (= 20x the earlier
  single-student probes; ~2x the estimated pilot peak of 280
  concurrent journeys spread over real users).
- Throughput plateaus ~65 RPS on ONE worker (full RAG pipeline
  included) — past that, requests queue and latency grows roughly
  linearly with concurrency; nothing breaks. Production compose runs
  2 workers (`WEB_CONCURRENCY`), i.e. ~2x these curves; the runbook's
  older containerized baseline (120 concurrent, p95 < 300 ms) measured
  a lighter mix on Linux — the honest combined story: **pilot load
  fits with margin, and the failure mode at overload is graceful
  queueing, then 429 backpressure.**
- Dev SQLite never errored (busy-timeout configured), consistent with
  the plan: Postgres at step-2 scale, not before.

## Leg 3 — LLM-down chaos (:8020, invalid Gemini key)

| Check | Result |
|---|---|
| `POST /tutor/ask` | **502 `llm_unavailable`** with safe message; repeatable, no key/error detail leaked, no 500 |
| `POST /quizzes` + submit | **200** both — quiz path is question-bank backed and survives LLM outage |
| `GET /health` / `GET /status` | 200 (see finding below) |

Finding (recorded, not fixed — design tension): `/status`'s assistant
component reports "provider configured" (presence check), so the
public status page stayed **ok** while real asks were failing. Making
it probe upstream would give an honest "degraded" signal but adds an
upstream call per status poll and (worse) a self-DoS vector on the
free tier. Options for the human: (a) accept (degradation is visible
in-app per request via the 502 copy), (b) add a cached 5-minute
upstream probe behind a flag. Recommendation: (a) for pilot.

## Verdicts

- 10x load: **PASS** (0 % errors at 2x pilot peak; documented
  graceful-degradation curve, backpressure verified).
- LLM-down degraded mode: **PASS** (structured 502, core journeys
  stay up) with one honest caveat about the status page.
- Staging-environment revocation/CDN chaos remains a **🖐 human/staging
  item** — there is no staging environment yet (hosting_decision.md
  unsigned).
