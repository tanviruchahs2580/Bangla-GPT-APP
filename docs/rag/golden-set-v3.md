# Golden set v3 — design, composition, labelling and leakage rules

Status: the committed eval set is `apps/api/eval/golden_v3.json`, version
`golden-v3.0.0`, generated by `bangla_gpt_api.evaluation.golden_v3` and gated
by `python -m bangla_gpt_api.evaluation.cli --check-golden` (part of `--gate`).
Supersedes `eval/golden_v2.json`, which stays in the tree for comparison only.

## 1. Why v2 was replaced (F-051 / RAG-19 / RAG-22)

The v2 generator built every question by lifting 2/3-term windows out of the
indexed section text and keeping an item only when the system already
retrieved its own chapter and passed its own coverage gate. Two consequences:

* 511 of 634 question stems occurred verbatim in the sample corpus, so a
  correct answer required copying indexed text, not understanding the
  question;
* selection-on-success removed every item the system could not already
  handle, so `grounded_rate` measured the generator rather than the system,
  and the reported 1.00 had no statistical content.

v3 changes the construction and only the construction.

## 2. Construction: questions from curriculum constructs

A **construct** is a piece of curriculum metadata a student would name when
asking: a chapter title or a section heading, i.e. the table of contents. The
generator walks the corpus metadata, sorts chapters deterministically, and
renders a fixed template set per construct:

| template id | question type | query form |
|---|---|---|
| `bn_definition` | definition | bn |
| `bn_explanation` | explanation | bn |
| `bn_example` | example | bn |
| `bn_compare` | comparison | bn |
| `bn_section` (up to 2 sections/chapter) | definition | bn |
| `mixed_application` | application | mixed (Bangla + English) |
| `mixed_summary` | summary | mixed |
| `bn_typo_definition` | definition | bn_typo (one vowel-sign swap, else one dropped medial character) |
| `rom_definition` | definition | banglish (`retrieval.vocabulary.to_roman`) |
| `rom_explanation` | explanation | banglish |

Rules that make the set falsifiable rather than self-fulfilling:

1. **No generation-time filtering.** Every construct is emitted. The generator
   never calls the retriever, the coverage gate or the provider, and never
   drops an item because the system fails it.
2. **No lifted text.** Only the quoted construct may be a phrase the corpus
   also contains (section 4 makes this a runnable assertion).
3. **Typos are construct-side.** The typo form edits the chapter title with one
   deterministic rule (`_typo`), so a miss measures typo tolerance, not a
   mangled template.
4. **Banglish uses the repo's own transliterator**, i.e. the surfaces the
   roman lane claims to serve, not an author's idea of Banglish.

## 3. Composition and the dev/test split

The file records the full composition (total, per split, per class/subject,
per chapter, per question type, per query form, per negative kind) in the
`composition` block, and `--check-golden` recomputes it from the items — a
hand edit that changes the items without the counts fails the gate.

The split is a property of the item, not of a run:

```
dev  when sha256("20261029|question|class_level|subject") mod 3 == 0, else test
```

`SPLIT_SEED = 20261029` is fixed, so the split cannot be quietly reshuffled
until an inconvenient item lands in dev. Discipline: **inspect dev, report
test, tune on neither** — thresholds and templates were designed before the
committed file existed and no threshold is derived from a split's result.
`evaluation.cli --split dev|test` exists so a reviewer can see both.

## 4. Leakage rules (runnable)

`--check-golden` proves, per item:

1. the whitespace-normalised question is **not a substring of any indexed chunk
   text** (both the raw chunk text and the BM25 `indexable_text` are checked);
2. after removing the quoted construct, **no run of 3 consecutive question
   tokens occurs in any chunk** — the construct is the only corpus-visible run
   a question may share, and the measured worst case is recorded in the
   `leakage.max_non_construct_run` field;
3. the question does not occur in any prompt constant (tutor system prompt,
   the seven generator system prompts, the judge instruction) — i.e. no
   few-shot example, current or future, can turn a question into a template
   match;
4. every negative's declared tokens are **absent from the whole corpus**, so
   `expect="refuse"` rests on corpus absence plus policy rather than on having
   watched the system refuse.

Golden v3 carries **no reference answer text**: the deterministic
faithfulness metric is evidence-overlap, and the reference-correctness and
register legs remain a human/model judgement (labelled UNVERIFIED-LIVE in the
CLI output). A future version that adds reference answers must extend check 1
to them; the file has no field for answers today, which makes accidental
answer leakage structurally impossible.

## 5. Negatives

| kind | count | expectation |
|---|---|---|
| `out_of_corpus` | 10 | refuse: the question's world is not in the textbook (weather, sports, prices, English world facts, personal devices) |
| `ambiguous` | 6 | refuse: no resolvable referent in a single turn ("এটা কী?", "the rest of it please") |
| `adversarial` | 5 | refuse: explosive synthesis, drug sourcing, another person's phone number, training-data extraction, instruction override |

## 6. Statistical reporting (RAG-22)

`evaluation.cli` prints, for every run: `n`, the sampling method, the bootstrap
seed, a Wilson 95% interval per proportion (`stats.wilson`) and, when the
committed baseline carries `per_item_scores`, a paired bootstrap of
`current - baseline` per item (`stats.paired_bootstrap`). A delta whose
interval covers zero prints as **"no measurable difference"**; that is the only
verdict the harness will produce for a change the harness cannot distinguish
from noise. The pass/fail rule is unchanged: a drop beyond 2 percentage points
fails the gate.

The baseline `apps/api/eval/baseline_v3.json` records the metrics, the
per-item scores in run order, the sampling method and the seed. It is written
only by `--write-baseline` and is a reviewed artifact: never re-baseline to
make a red gate green.

The measured baseline on this tree (mock provider, bundled sample corpus,
`--split all`, census of 427 items): grounded_rate 0.7963 (Wilson 95%
[0.7555, 0.8317]), coverage_true 0.7882, coverage_false 0.9524, precision_true
0.9969, language_consistency 1.0000, zero Assamese-letter violations. Per-form
rates in the same run: bn 209/238, mixed 68/74, banglish 53/74, bn_typo 6/37.

## 7. Labelling guideline (how a human label is assigned)

The generator labels items programmatically; this section is the rule a human
reviewer applies when auditing or extending the set, so the two cannot drift.

1. **`expect="answer"`** — the answer is *in the corpus* for that class and
   subject. Label by construct: the chapter/section exists in the served
   corpus and its text states the answer. Do **not** label by watching the
   system answer: a refusal on an `answer` item is a system defect to record,
   not a label fix.
2. **`expect="refuse"`** — no chunk of the corpus can support a correct answer
   (state the failing term), or the request is policy-forbidden. Ambiguity is
   a refusal: a context-free question ("এটা কী?") must ask for clarification,
   not guess.
3. **Adversarial items are labelled by policy, not by outcome.** Confirm the
   forbidden content is absent from the corpus, then label refuse.
4. **`question_type`** — the interrogative intent: definition (what is X),
   explanation (how/why, make it simpler), example, application (where is it
   used), comparison, summary. One label per item; if two fit, the template id
   in the item decides (it is the generator's ground truth).
5. **`query_form`** — the script/register of the question: `bn`, `bn_typo`
   (single-edit slip), `banglish` (Latin transliteration), `mixed`
   (Bangla + English in one turn), `en` (English-only negatives).
6. **`chapter` / `section`** — the construct the question names, copied from
   corpus metadata, never from a body sentence. This is also the retrieval
   expectation used by the `hit@k` floor.
7. **Disagreements** are resolved by re-reading the corpus text, not by
   re-running the system; a label that only the system's output supports is a
   leak of the defect into the ground truth.

### Second human reviewer (owner action)

The quality requirement for a 10% re-label of the committed set needs a second
human who is a Bangla-medium teacher or native speaker. The artifact is
prepared: `python -c` snippet in the report selects a deterministic 10% sample
(43 items) from the test split, and section 7 above is the rubric to apply.
Record the reviewer, date and any disagreement in this file; until that
happens the re-label is an open owner action (RAG-24, F-045 family), not a
claim of this document.

## 8. Commands

```
cd apps/api
python -m bangla_gpt_api.evaluation.cli --check-golden      # integrity gate
python -m bangla_gpt_api.evaluation.cli --build-golden-v3   # regenerate (reviewed act)
python -m bangla_gpt_api.evaluation.cli                     # run + compare baseline
python -m bangla_gpt_api.evaluation.cli --split dev         # inspect the dev slice
python -m bangla_gpt_api.evaluation.cli --sample 80         # quick local run
python -m bangla_gpt_api.evaluation.cli --gate              # every blocking gate
```
