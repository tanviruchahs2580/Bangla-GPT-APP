### A-4 (operational, S2, fixed on the live host): the deployed database was never under migration control

`alembic upgrade head` — step one of the documented deployment procedure — **fails against the
production database**: its `alembic_version` table is empty while the schema already exists, so
Alembic replays from the initial revision and dies on `table users already exists`. The schema
had been assembled by the application's own bootstrap plus partial runs, which is why it
contains some later columns and not others. The new code needs two columns that were absent, so
leaving it would have broken every sign-in on the live deployment.

Handled conservatively: two backups first, then the schema difference between the live database
and a properly migrated one was computed (exactly two columns, both additive and defaulted, on
`users`), the same `ALTER TABLE … ADD COLUMN` the migration performs was applied, and the
database was stamped at head. Ten rows preserved, `alembic check` now reports no drift. What is
missing and recommended for the owner: a runbook procedure for exactly this case ("adopt an
unmanaged database: diff, reconcile, stamp") — the runbook documents migration and rollback but
assumes the database was created by Alembic in the first place.
